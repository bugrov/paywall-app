# Состояние проекта

Журнал этапов. Обновляется в конце каждого этапа, до показа пользователю.

## Решения (действуют на весь проект)
- Концепт: №1 «Комета Кузя» (космос, тёмно-синий фон, оранжевая комета). Выбран пользователем 2026-10-12.
- Пакетный менеджер: npm. БД: Neon Postgres через Vercel Marketplace, без ORM.
- Стили: обычный SCSS (scoped) + БЭМ + миксины, `toRem()`. Tailwind пробовали (через `@apply`) и убрали
  по решению пользователя: stylelint-конфиг заточен под обычные стили. Nuxt UI и Pinia не используем.
- Git: всё в `main`, один коммит на этап, пуш только после ОК пользователя.
- Скиллы и правила лежат в репозитории (`.claude/skills`).
- Тарифы лежат в коде (`server/utils/offers.ts`), в БД только покупки: по заданию тарифы грузятся через
  server route, а paywall не должен зависеть от доступности базы.

## Этап 4. Backend и БД
- Сделано: Neon Postgres подключён к Vercel-проекту `paywall-app` (integration из Marketplace, переменные
  `DATABASE_URL` и др. в Vercel и локально в `.env`). Таблица `purchases(id uuid, offer_id, device_id,
  idempotency_key unique, created_at)` + индекс по `(device_id, created_at desc)`, создаётся лениво.
  `POST /api/purchase` пишет в БД, идемпотентен по `Idempotency-Key` (insert ... on conflict do nothing,
  затем чтение исходной строки; другие данные при том же ключе дают 409). `GET /api/purchases?deviceId=`
  и рабочая кнопка «Восстановить покупки» (нашлись покупки: экран успеха; нет: сообщение).
- Проверено на реальной базе: покупка 200 и запись есть; повтор с тем же ключом возвращает ту же
  покупку; тот же ключ с другим тарифом 409; нет ключа, плохой deviceId, нет deviceId 400; 8 параллельных
  запросов с одним ключом дали 1 строку; восстановление находит покупки своего устройства и не видит
  чужие; UI-сценарий (покупка, перезагрузка, восстановление, чужое устройство) в Playwright.
- Решения: Neon HTTP-драйвер без ORM (одна таблица); схема создаётся при первом запросе, чтобы деплой не
  требовал миграции; deviceId приходит от клиента (UUID из cookie) и не является секретом, по нему
  отдаются только `offerId` и время покупки; клиент передаёт deviceId в теле/запросе, а не читается из cookie
  на сервере, чтобы API работало и там, где cookie недоступны.
- Побочное: Vercel CLI при установке интеграции дописывал `.env*` в `.gitignore` (перекрывало
  `.env.example`) и клал сторонние файлы навыков Neon в репозиторий: откатил и удалил.

- Сделано: README до одной страницы (запуск, структура, платформа и БД, AI-инструменты и проверки,

- Ревью шестью проходами (наш скилл `paywall-review` и агенты плагинов: логика, тихие сбои, соответствие

- Исправлено по ревью:
  - клиент: таймаут 15 с у запросов, проверка формы ответов (массивы, `purchaseId`), логирование ошибок,
    сброс `Idempotency-Key` при 4xx, пустой список тарифов считается сбоем, а не вечной загрузкой;
  - сервер: `isError` из h3, `useDb()` внутри `try`, лимит тела 1 КБ (413), `no-store` на
    `/api/purchases`, `max-age=300` на `/api/offers`, заголовки `nosniff` и `Referrer-Policy`,
    схема БД одним запросом-транзакцией, нейтральный текст 500 при отсутствии конфигурации;
  - прочее: `engines` и `.nvmrc`, `robots noindex`, `styles: ['normal']` у шрифтов, миксин `tap-target`
    задействован, документация и комментарии приведены к факту.
- Не делали сознательно: rate limit в коде (в serverless in-memory бесполезен, нужен Vercel Firewall),
  серверная HttpOnly-cookie вместо deviceId в запросе, логика «уже куплено» на том же устройстве,
  таблица `offers`, миксин для общих стилей карточки и скелетона (7 строк), X-Frame-Options.
- `npm audit --omit=dev`: critical/high только в build- и dev-зависимостях Nuxt (devtools, nitropack,
  simple-git, stylelint); в деплоимом `.output/server/node_modules` их нет. Единственная рекомендация
  audit (`nuxt@3.7.4`) это даунгрейд, не применялась.
- Node: Nuxt 4.6.1 требует `^22.22.3 || ^24.15.0 || >=26`; локально 22.15 даёт предупреждение.
